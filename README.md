只使用虛擬籌碼的德州撲克（No-Limit Hold'em）AI 研究與模擬平台。設計依據為〈Poker AI 平台技術設計文件〉。

## 快速開始

需要 Python 3.12 以上；網頁前端另需 Node.js 22。引擎本身零外部依賴。

```bash
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\Activate.ps1
pip install -e ".[web,sim,solver,dev,oracle]"
```

### 網頁牌桌（M2）

先建置前端，再啟動伺服器，然後開啟 http://127.0.0.1:8000 ：

```bash
cd frontend && npm install && npm run build && cd ..
uvicorn --factory backend.api.app:create_app
```

環境變數：`POKER_DB_URL`（預設 `sqlite:///poker.db`，PostgreSQL 用 `postgresql+psycopg://…`）、`POKER_AI_DELAY`（AI 每個動作前的等待秒數，預設 0.6，牌桌上也能調整）。啟動時會自動執行 Alembic 遷移。

開發前端時可另開 `npm run dev`（Vite 會把 `/api` 與 `/ws` 轉給 :8000）。

### 測試

```bash
scripts/run_tests.sh               # Windows: scripts\run_tests.ps1
```

端對端測試需要建好的前端與 Playwright Chromium（`python -m playwright install chromium`）；缺少時會自動跳過。Linux 若缺系統函式庫，執行 `sudo .venv/bin/python -m playwright install-deps chromium`。

### AI vs AI 模擬（M3）

```bash
python -m backend.arena rule random station --deals 20000 --seed 1 --out out/arena/run1 --db sqlite:///poker.db
```

Agent 寫成 `kind` 或 `name=kind`（kind：`rule`、`random`、`station`），同一種可用不同名字重複出現。每個 deal 會依座位輪換打 N 次（N = Agent 數），所以總手數 = deals × N。`--workers` 預設使用全部 CPU，`--boundary process` 讓每個 Agent 在獨立行程執行。

### Preflop push/fold 求解（M4）

已求解的資料放在 `data/preflop/pushfold/`。重新求解（約 2 小時，使用全部 CPU）：

```bash
python -m backend.solver pushfold --players 2-9 --stacks 5,8,10,12,15,20 --db sqlite:///poker.db
```

Arena 與網頁牌桌都能選用 `pushfold` Agent。

### Kuhn / Leduc 與單挑翻後子賽局（M5）

```bash
python -m backend.solver small leduc --iterations 3000
python -m backend.solver subgame --board Ks7d4c2h --oop "22+,A2s+,K9s+,ATo+" --ip "22+,A2s+,K5s+,A9o+" \
    --pot 10 --stack 40 --bets turn=50,100 river=50,100 --raises turn=100 river=100 --target 0.3
```

加上 `--db sqlite:///poker.db` 會以 request hash 快取結果，相同請求直接讀取。

子賽局預設使用批次化的 PyTorch 版本（有 CUDA 就用 GPU），`--device numpy` 改用 NumPy 參考實作。安裝 GPU 版 PyTorch：

```bash
pip install torch --index-url https://download.pytorch.org/whl/cu128
```

### GTO 資料集（M6）

```bash
python -m backend.dataset build out/datasets/gto-postflop-hu-v1 --spots 1000 --seed 1
python -m backend.dataset validate out/datasets/gto-postflop-hu-v1 --db sqlite:///poker.db
```

`build` 中斷後重新執行同一行指令，只會補算缺少的分片；`validate` 全部通過才會登記到資料庫。

### GTO Policy Network（M7）

```bash
python -m backend.policy prepare out/datasets/gto-postflop-hu-v1 out/datasets/gto-postflop-hu-v2 --out out/policy/v1v2-features.npz
python -m backend.policy train out/policy/v1v2-features.npz out/policy/run-v1v2 --hidden 512 --dropout 0.3 --db sqlite:///poker.db
python -m backend.policy benchmark out/policy/run-v1v2/model.pt
```

`train` 中斷後用同一行指令會從 `checkpoint.pt` 續訓（設定不同會拒絕）。

### 對手建模（M8）

```bash
python -m backend.opponent accept --out out/opponent/acceptance.json   # 驗收實驗，約 6 分鐘（24 核心）
python -m backend.arena style-lag rule --deals 1000                    # 風格 Agent：style-nit/tag/lag/station/maniac
```

網頁對戰每存一手牌，就把公開統計加進每位玩家的 `player_statistics`，並更新 `opponent_models` 的後驗（在背景的單一工作執行緒依序處理，不延遲牌局畫面）。

### 即時求解 Agent

Arena 與網頁大廳都能選用：`realtime`（即時求解，網路備援）與 `neural`（只用網路，用來比較）。

```bash
python -m backend.arena realtime rule --deals 100 --workers 1
```

### CLI 示範

隨機 Agent 對戰，輸出 JSON 手牌紀錄：

```bash
python -m backend.cli --players 6 --hands 5 --seed 42 --out out/hands.jsonl
```

## 引擎介面

```python
state.legal_actions() -> LegalActions   # can_fold, can_check, call_amount, min_raise_to, max_raise_to
state.apply(Action) -> list[Event]      # 非法動作丟出 IllegalActionError，不會靜默修正
state.observation(seat) -> PlayerView   # 只含該座位可見資訊
state.result() -> HandResult            # 底池分層、贏家、每人淨輸贏
```

BET / RAISE 的 `amount` 是「加注到」的本輪總額。全下不是獨立動作，`state.all_in_action()` 會轉成對應的 CALL / BET / RAISE。

## 規則決策與已知簡化

| 規則 | 實作 |
|---|---|
| 籌碼 | 全部為整數 |
| 大盲不足額 | 翻前仍需跟滿整個大盲（Robert's Rules）；最小加注增量為 1 BB |
| 不足額全下 | 不改變最小加注增量；已行動者只有在累計被加注量達到一次完整加注時才重新開放加注（TDA 累計規則） |
| 無人可對抗 | 其他仍在牌局的玩家都無法再投入超過目前注額（已全下或籌碼不足）時，只能跟注或棄牌 |
| 強制過牌 | 注額已平且沒人能回應加注時，跳過該玩家，不要求無意義的過牌 |
| Heads-Up | 按鈕位下小盲、翻前先行動、翻後最後行動 |
| 未被跟注的下注 | 每輪結束時退回 |
| 側池 | 依每位未棄牌玩家的總投入切分；棄牌者籌碼留在池中但無資格分配 |
| 零頭 | 每個底池分別平分，零頭從按鈕左側第一位贏家起依序每人 1 枚 |
| 攤牌 | 簡化：進入攤牌的玩家全部亮牌 |
| 按鈕 | 簡化：每手移到下一位在桌玩家；不實作死按鈕 / 補盲 |
| Ante | 尚不支援（參數保留） |
| 離桌 / 暫離 | 牌局中提出離桌，該手結束後生效；輪到時自動過牌或棄牌。籌碼歸零者自動暫離，補籌碼後可重新加入 |

## M1 驗收結果

- **評估器**：10 萬組隨機 7 張牌與「21 組 5 張牌暴力組合」參考實作比對一致；另與 PokerKit 評估器交叉比對 3,000 組。
- **情境測試**：每條規則決策至少一個手寫情境（`tests/test_hand_scenarios.py`）。
- **模糊測試**：1 萬手隨機 2～9 人、隨機籌碼與盲注；每個動作後檢查籌碼守恆、底池非負、行動者合法、觀測不洩漏他人手牌，並以 JSON 紀錄重播比對事件與結果完全相同。
- **PokerKit 差分測試**：1 萬手，9,975 手最終籌碼完全一致；其餘 25 手只差在零頭落點（每人差距不超過該手零頭數）。

### 與 PokerKit 的已知差異（書面解釋）

1. **大盲不足額**：PokerKit 只要求跟到大盲實際下的金額，我們要求跟滿整個大盲。這類手牌（約 8%）不納入比對，改由情境測試 `test_short_big_blind_must_be_called_in_full` 覆蓋。
2. **零頭**：PokerKit 在輸家蓋牌後會把贏家相同的邊池合併，且把整份零頭給同一位贏家；我們每個邊池分別計算，並逐枚分配。總額相同，只有零頭落點不同。
3. **強制過牌**：沒人能回應加注且注額已平時，我們跳過該玩家；PokerKit 仍要求一次過牌。差分測試會自動補上這一步。
4. **單挑且大小盲相同**：PokerKit 以盲注大小判斷單挑的按鈕位，無法對應，這類手牌不納入比對。

### 效能基準（M3 參考值）

純 Python 單核心、隨機 Agent、含 JSON 紀錄：6～9 人約每秒 2,600 手；單挑深籌碼約每秒 900 手（隨機 Agent 會反覆加注）。

## M2 驗收結果

- **資料庫**：`players`、`poker_tables`、`games`、`hands`、`actions` 五張表（設計文件第 6 節中 M2 用得到的部分），以 Alembic 遷移建立。每手只存「種子 + 起始籌碼 + 動作序列」與衍生結果；讀取時重播並核對結果，不一致會直接報錯。
- **資訊隔離**：瀏覽器收到的 JSON 只從 `PlayerView` 產生，AI 也只拿得到自己的觀測。API 測試與 Playwright 測試都會在每手結束後，用伺服器端的真實手牌比對**每一個** WebSocket 訊框與畫面上的每張牌：未攤牌的對手手牌從未出現，攤牌的牌只在本手結束後出現。刻意把視角換成別的座位時，兩組測試都會失敗（突變測試已驗證）。
- **桌面與手機**：Playwright 以 1280×800 與 390×844 兩種尺寸各打完兩手、補充籌碼、瀏覽歷史並逐步重播，且無水平捲動。
- **其他**：伺服器重啟後牌桌可從資料庫恢復（籌碼、手數、按鈕位置）；非法動作會回傳錯誤訊息，不會改變狀態；Windows 與 Linux 都通過後端測試。

M2 的 AI 只有基準 Agent（隨機、跟注站），策略型 AI 從 M4 開始。AI 籌碼歸零時會自動補回起始籌碼；你則需按「補充籌碼」。

## M3 驗收結果

**方法**：鏡像牌局（duplicate）。每個 deal 用同一副牌，讓 Agent 依座位循環輪換各打一次，每個 Agent 都會在每個位置拿到每個座位的牌；每手籌碼重設為 100 BB，按鈕固定在 0 號座位。所有隨機來源都由主種子依（deal、輪換、Agent）派生，與 worker 數量和分批方式無關。

**統計**：同一 deal 的各手彼此相關，所以以 deal 為獨立單位：取每個 Agent 在該 deal 的平均輸贏，再以這些區塊平均值的平均數與標準誤，搭配 Student-t 分位數計算 95% 信賴區間。

- **同種子結果完全相同**：1、3、4、16 個 worker 跑出的逐手資料與統計逐位元相同；換種子則不同。同一組設定在 Windows 與 Linux 上的結果也完全一致。
- **輸出 bb/100 與 95% 信賴區間**：CLI、`summary.json` 與資料庫 `benchmark_results` 都有 bb/100、標準差、信賴區間；以已知平均的合成資料重複 2,000 次，區間涵蓋率落在 93.5%～96.5%。
- **鏡像牌局正確**：相同且決定性的 Agent（2、3、6 人）每個 deal 的淨輸贏都**剛好為 0**；每手零和；每個 Agent 坐過每個座位。
- **可重播**：`hands.parquet` 每列保存牌堆種子與動作序列，測試逐手重建後與 `players.parquet` 的輸贏完全一致。
- **隔離**：`inline` 模式下 Agent 拿到的是不可變的 `PlayerView`，改不動牌局；`process` 模式下 Agent 在獨立行程，只透過 JSON 資料溝通。兩種模式的結果完全相同（同時證明 Agent 只依賴可序列化的資料）。
- **紀錄**：每次模擬記錄主種子、git commit（有未提交變更時加 `-dirty`）、Agent 設定與耗時（資料表 `simulation_runs`、`benchmark_results`，Alembic 遷移 0002）。

### 基準結果（種子 1）

| 對戰 | 手數 | 結果（bb/100，95% 信賴區間） |
|---|---|---|
| 單挑 rule vs station | 100,000 | rule +153.7 [149.0, 158.3] |
| 單挑 rule vs random | 100,000 | rule +107.5 [98.8, 116.1] |
| 6 人 rule×2、random×2、station×2 | 120,000 | rule +516 / +507；station +66 / +45；random −535 / −599 |

## M4 驗收結果（第一階段：短籌碼 push/fold）

**資料調查（2026-10-15）**：沒有找到授權明確、且由 Solver 產生的 9-max preflop 資料。[Rizehigh/gto-preflop-trainer](https://github.com/Rizehigh/gto-preflop-trainer) 雖為 MIT 授權，但未說明頻率來源；TexasSolver 內附的 6-max 範圍，維護者表示不清楚來源與求解設定（[Issue #11](https://github.com/bupticybee/TexasSolverGPU/issues/11)）；其餘多為商業產品。因此依設計文件第 10 節自行求解，不使用來源不明的資料。

**求解的遊戲**：2～9 人、等效籌碼 5／8／10／12／15／20 BB、盲注 0.5/1、無 Ante。每位玩家只能棄牌或全下（面對全下時棄牌或跟注）。全下一律打到攤牌，所以報酬是精確的 chip EV，不需要翻後模型。共 48 組設定。

**方法**：external-sampling MCCFR（線性加權），多進程同步批次。每位玩家只行動一次，所以平均策略就是各批當前策略的線性加權平均。

**驗收：每筆策略都附來源與授權；沒有資料的地方標為近似，不假造**

- **來源與授權**：每個資料檔都記錄 `strategy_source = solver_approx`、求解器名稱與設定、授權（本專案自行產生，不含第三方資料）、遊戲定義、request hash 與收斂指標。資料庫 `gto_datasets` 登記每個資料集，`solver_results` 以 request hash 快取完整結果（Alembic 遷移 0003）。
- **收斂指標**：以兩半獨立樣本估計每位玩家偏離策略可多得的 EV，回報區間：上界（同一份樣本取最大值，雜訊會讓它偏高）與下界（一半選策略、另一半計分）。單挑全部落在 ±0.007 bb/hand 內；9 人桌單一位置最多約 0.06 bb/hand。
- **不假造**：求解時很少走到的格子（例如已有多人跟注全下的分支）存成空值。9 人桌約 75% 的格子是這種罕見分支。
- **Agent 標示**：`PushFoldAgent` 只在已求解的情境使用資料並標為 `SOLVER_APPROX`，附上動作機率。深籌碼、limp、非全下的加注、翻後，以及空值格子，一律退回規則型策略，標為 `HEURISTIC`，並寫明原因（例如「no solved data (effective stack 100.0bb outside solved depths)」）。
- **獨立驗證**：單挑 10 BB 另以「類別對類別勝率矩陣 + 全寬度 CFR+」精確求解：SB 全下 58.2%、BB 跟注 37.3%，與已發表的單挑 push/fold Nash 結果相符。MCCFR 的策略用這個矩陣精確計算，可被剝削量只有 0.002 bb/hand。

### 對戰結果（10 BB，鏡像牌局，95% 信賴區間）

| 對戰 | 結果（bb/100） |
|---|---|
| 單挑 pushfold vs rule | pushfold +27.2 [26.3, 28.1] |
| 單挑 pushfold vs random | pushfold +18.8 [15.7, 22.0] |
| 單挑 pushfold vs station | pushfold +86.5 [83.1, 89.9] |
| 9 人：pushfold×3、rule×3、station、random×2 | pushfold +21～+26；rule +11～+14；station −4；random −51～−54 |

均衡策略的目的是不被剝削，而不是剝削對手，所以對隨機 Agent 的優勢小於對跟注站。

### 限制與後續

- 只涵蓋 5～20 BB 的 push/fold。深籌碼（例如 100 BB）的 preflop 需要翻後模型，計畫在 M5 的翻後 Solver 完成後再處理；在那之前，深籌碼一律標為 `HEURISTIC`。
- 假設所有玩家籌碼相同；實際牌局取「我的籌碼與最大對手籌碼的較小值」，對應到最接近的已求解深度（相差超過 25% 就不使用）。
- 無 Ante、chip EV（不含 ICM）。

## M5 驗收結果

**驗收：Kuhn / Leduc exploitability 收斂；單挑子賽局附收斂指標**

### Kuhn 與 Leduc（表格式 CFR+，精確 exploitability）

規則與動作編碼完全依照 OpenSpiel 的 `kuhn_poker`、`leduc_poker`。整棵賽局樹都列舉出來，所以 best response 與 NashConv 是精確值。只有 NashConv 低於門檻（預設 10⁻³）的結果才標為 `VERIFIED_EQUILIBRIUM`，否則標為 `SOLVER_APPROX`。

| 遊戲 | 迭代 | NashConv | 先手期望值 | 已知值 | 標示 |
|---|---|---|---|---|---|
| Kuhn | 2,000 | 8.7×10⁻⁵ | −0.05556 | −1/18 | verified_equilibrium |
| Leduc | 3,000 | 1.6×10⁻⁴ | −0.08561 | −0.0856 | verified_equilibrium |

- **Kuhn 對照解析解**：先手用 J 詐唬的頻率 α 落在 [0, 1/3]，K 下注頻率 ≈ 3α，Q 從不下注，被下注時 Q 以 α + 1/3 跟注；後手 J 詐唬與 Q 跟注都是 1/3。
- **與 OpenSpiel 交叉驗證**：每個節點的合法動作、輪到誰、終局報酬都和 OpenSpiel 一致；把我們的平均策略載入 OpenSpiel，它算出的 NashConv 與我們的值相差不到 10⁻⁹。OpenSpiel（Apache-2.0）只用在測試，不是執行時依賴。

### 單挑翻後子賽局

- **方法**：向量化 CFR：每個公開節點對全部 1,326 組底牌各存一列策略，遍歷時傳遞整個 reach 向量。預設 DCFR（α=1.5、β=0、γ=2），也可選 CFR+。
- **精確的牌張移除**：終局只計算與自己底牌、公共牌都不衝突的對手組合；機會節點會發出每一張剩餘的牌。攤牌與棄牌的向量化計算，與逐組合暴力計算的結果完全一致。
- **收斂指標**：以精確的向量 best response 計算 exploitability（佔底池百分比），並保存收斂歷程；可設定目標值，提早停止。
- **理論對照**：河牌「極化範圍 vs 抓詐唬」玩具賽局，下注一個底池時，理論上詐唬佔下注範圍 1/3、跟注頻率 1/2、OOP 不主動下注。求解結果：詐唬比例 0.333、跟注 0.50、OOP 100% 過牌，exploitability 0.02% 底池。
- **實際轉牌局面**（Ks7d4c2h，底池 10、籌碼 40，兩種下注尺寸加一種加注，2,990 個決策節點）：

| 迭代 | DCFR（% 底池） | CFR+（% 底池） |
|---|---|---|
| 50 | 2.23 | 4.13 |
| 100 | 0.62 | 1.39 |
| 150 | 0.31 | 0.74 |
| 200 | 0.18 | 0.48 |

### GPU 加速

同一條下注路線之後的子樹，對每一張可能發出的轉牌或河牌結構都相同，所以把它們合併成一個「模板節點」，張量多一個 board 維度（每列一個公共牌面）。上面的轉牌局面從 2,990 個節點變成 76 個模板；整個迭代再用 CUDA Graph 錄下來重播，省掉數千次 kernel 啟動。

| 實作（Ks7d4c2h 轉牌局面） | 每次迭代 |
|---|---|
| NumPy 參考實作 | 約 1,200 ms |
| 批次化 PyTorch（CPU） | 約 340 ms |
| 批次化 PyTorch（RTX 4060 Laptop，逐個啟動 kernel） | 約 230 ms |
| 批次化 PyTorch（RTX 4060 Laptop，CUDA Graph） | **約 19 ms** |

- **正確性**：批次版本以 float64 在 CPU 執行時，DCFR 的 exploitability 與策略和 NumPy 參考實作一致到 10⁻⁹；CUDA Graph 與逐個啟動的結果一致到 float32 精度。CFR+ 會把 regret 截在 0，10⁻¹³ 的加總順序差異可能讓某手牌在「0」與「極小正值」之間切換，所以 CFR+ 的比對容許較大誤差。
- **翻牌局面**（Ks7d4c，底池 10、籌碼 90；NumPy 版本在這個規模不實用）：

  | 下注樹 | 模板 | regret＋策略 | GPU 峰值 | 每次迭代 | 100 次迭代 |
  |---|---|---|---|---|---|
  | 每條街一種尺寸、不加注 | 78 | 3.2 GB | 4.5 GB | 1.2 秒 | 0.64% 底池 |
  | 每條街一種尺寸＋一次加注 | 134 | 5.5 GB | 7.4 GB | 2.1 秒 | 1.47% 底池 |
- **記憶體上限**：建樹時先估算 regret 與策略需要的記憶體，超過上限（預設 6 GB）就拒絕並說明，而不是在 GPU 上耗盡記憶體。

### 限制與後續

- 翻牌局面的記憶體隨下注尺寸與加注次數快速成長；多尺寸的翻牌樹需要更大的 GPU，或花色同構、半精度儲存等減量手段。
- 固定下注尺寸的抽象樹，結果標為 `SOLVER_APPROX`；對手使用樹外的尺寸時，需要 action translation（設計文件第 10 節），留待接上 Agent 時實作。
- TexasSolver（AGPL）的 CLI 對照尚未接上；目前以解析解、OpenSpiel 與暴力計算驗證。

## M6 驗收結果

**驗收：機率總和、合法性、牌衝突檢查全過；可中斷續跑**

### 流程

1. **產生題目**：題目編號 `index` 在種子 `seed` 下永遠產生同一題：街道（河牌 70%、轉牌 30%）、公共牌、籌碼底池比（河牌 0.5～4、轉牌 1～8）、雙方範圍。
2. **求解**：用 GPU 批次求解器求解，直到 exploitability ≤ 0.5% 底池或達到迭代上限。下注抽象：河牌 33／75／150% 底池、轉牌與河牌 50／100% 底池，各街一次 100% 底池加注，並可全下。
3. **抽出資料**：每個第一條街的決策節點一列，包含雙方在該節點的 reach（1,326 維，float16）、行動者每組底牌的動作機率（float16）、每組底牌每個動作的 EV（籌碼，float32；沒有相容對手組合時為 NaN）。
4. **分片寫入**：每 50 題一個 Parquet 分片，先寫暫存檔再改名，所以分片只要存在就是完整的；重新執行只補算缺少的分片。設定不同的資料夾會拒絕混用。
5. **驗證後登記**：全部通過才寫入資料庫 `gto_datasets`（版本、來源、授權、筆數、路徑、設定、git commit、驗證結果）。

### 驗證項目（每一列都檢查）

- **機率**：每個值在 [0, 1]；行動者在該節點可能持有的每組底牌，動作機率加總為 1（float16 容差 0.01）。
- **合法性**：從題目重建下注樹，節點路徑、動作清單、雙方投入都必須一致；只有面對下注時才能棄牌，不面對下注時才能過牌。
- **牌衝突**：與公共牌衝突的底牌組合，reach 必須為 0。
- **數值**：reach 不為負；行動者可能持有且有相容對手組合的底牌，EV 必須是有限值。
- **完整性與收斂**：每個分片、每一題、每題的根節點都在；回報未達收斂目標的題數。
- **驗證器本身會抓錯**：測試刻意破壞資料（機率改壞、在衝突牌上放 reach、動作清單換成棄牌、不存在的節點、負的 reach、刪掉分片），每一種都被抓到並給出對應的錯誤訊息。

### 中斷續跑

- 測試在第二個分片中途模擬中斷：第一個分片保留、第二個分片沒有留下半成品；續跑後的每個分片與一次跑完的結果逐位元相同（CPU）。
- 實際建置 V1 時也真的中斷過一次（見下方），用同一行指令續跑完成。

| 項目 | 數值 |
|---|---|
| 題目 | 1,000（河牌 678、轉牌 322） |
| 資料列 | 11,992（每題約 12 個節點） |

- **只有轉牌與河牌**：翻牌題目的記憶體與時間成本高，V1 未納入。
- **只抽第一條街的節點**：轉牌題目中河牌的節點沒有抽出。

## M7 驗收結果

**驗收：驗證集 KL 與 EV regret 達標；CPU 單次推論 < 100 ms**

設計文件沒有寫具體門檻，所以在**訓練之前**先訂好目標，之後沒有再調整：

| 指標 | 目標 | 結果（測試集 500 題） |
|---|---|---|
| KL（solver 策略 ‖ 模型策略），依到達機率加權 | ≤ 0.15 nats | **0.093** ✅ |
| EV regret：Σ (solver − 模型) × 動作 EV，佔底池 | ≤ 1% | **0.19%** ✅ |
| CPU 單次決策（含特徵計算，全新牌面） | < 100 ms | **p95 約 73 ms、最大 78～85 ms** ✅ |

### ⚠️ 實際可被剝削量：離 GTO 還很遠

上面的 KL 與 EV regret 衡量的是「模型多像 solver」。EV regret 假設對手與之後的每一步都照 solver 打；但最佳回應的對手會專門針對模型的偏差。所以另外把網路的策略寫進賽局樹的**每一個**決策節點（每個節點用網路自己的策略推出的範圍），再對雙方算精確的 best response：

```bash
python -m backend.policy exploit out/policy/run-v1v2/model.pt --seed 2 --max-index 4000 --spots 160
```

| 測試題（V2 測試集） | 題數 | solver 可被剝削量（% 底池） | **網路可被剝削量（% 底池）** | 網路 ≤ 1% 的題目 |
|---|---|---|---|---|
| 河牌 | 108 | 中位數 0.20、最大 0.50 | **中位數 9.6**、平均 15.3、p90 35.2 | 1% |
| 轉牌 | 52 | 中位數 0.31、最大 0.50 | **中位數 47.0**、平均 60.3、p90 134 | 0% |

**結論：模型本身的策略離近似均衡還很遠**，河牌約是 solver 的 50 倍，轉牌更糟。超過 100% 底池是因為籌碼可以到底池的 8 倍。原因：

- 均衡的關鍵在無差異點的混合比例（例如詐唬比例、跟注頻率）；這裡差一點點，對照 solver 的對手幾乎沒影響（所以 EV regret 很小），但最佳回應會立刻改成「永遠跟」或「永遠棄」來剝削。
- 誤差沿著賽局樹累積：模型在後面的節點，看到的是自己策略推出來的範圍，和訓練時的均衡範圍不同。
- 轉牌題裡的河牌節點不在訓練資料中（資料集只抽第一條街），而且要走兩條街。

這個工具本身經過驗證：把 solver 自己的策略寫回同一棵樹，得到的可被剝削量與 solver 完全相同；均勻隨機策略則遠高於 solver（`tests/test_policy.py`）。

**因此實際對戰的 Agent 改成以即時求解為主、網路為輔**，設計見 [`docs/realtime-agent.md`](docs/realtime-agent.md)。

### 模型與資料

- **輸入**：手牌與公共牌、牌型類別、牌力百分位、對對手範圍的精確勝率（轉牌對每張河牌平均，含牌張移除）、底池幾何（面對下注與否、跟注額、SPR、雙方投入）、合法動作遮罩、雙方範圍（各一層線性嵌入），以及「範圍對範圍」勝率直方圖（雙方各 10 格，描述範圍優勢與堅果優勢）。
- **輸出**：固定 10 個動作欄位（f、x、c、b33、b50、b75、b100、b150、r100、a），不合法的遮掉。
- **網路**：MLP（3 層 × 512、dropout 0.3），參數約 85 萬。
- **損失**：對 solver 混合策略的交叉熵，依「帶著這手牌到達這個節點的機率」加權。
- **資料**：V1＋V2 共 5,000 題、59,050 個節點、約 2,450 萬筆（節點 × 底牌組合）。**依題目切分**：10% 測試（只在最後評估）、10% 驗證（選最佳 epoch）、80% 訓練，同一題不會出現在兩個集合。
- **訓練**：RTX 4060 Laptop 約 5 分鐘（12 個 epoch）；驗證 KL 到最後一個 epoch 仍在下降，沒有過擬合。

| | KL | EV regret |
|---|---|---|
| **模型** | **0.093** | **0.19%** |
| 同類節點平均策略（基準） | 0.531 | 7.60% |
| 合法動作均勻隨機（基準） | 0.868 | 10.43% |

| 節點類型 | KL | EV regret |
|---|---|---|
| 河牌、不面對下注 | 0.083 | 0.14% |
| 河牌、面對下注 | 0.044 | 0.13% |
| 轉牌、不面對下注 | 0.143 | 0.22% |
| 轉牌、面對下注 | 0.128 | 0.49% |

**標籤雜訊下限**：同一題用兩種演算法（DCFR、CFR+）各自求解到 ≤ 0.5% 底池，兩者策略的 KL 約 0.03 nats。接近無差異的手牌，混合比例本來就不唯一，所以 KL 不可能降到 0。

| 改動 | 資料 | KL | EV regret |

### 推論速度

為了讓轉牌也能用精確勝率，新增 `fast_eval.py`：NumPy 向量化的 5～7 張牌評估（約每秒 100 萬手，分數與原評估器逐一相同），以及對範圍的精確勝率（與逐手暴力計算相差 10⁻¹⁴）。轉牌的牌面前處理（48 張河牌 × 1,081 組合）用兩個執行緒，約 20 ms。

| 情境（CPU） | p95 |
|---|---|
| 河牌，全新牌面 | 約 6 ms |
| 轉牌，全新牌面 | 約 73 ms |
| 同一牌面上的後續決策 | 約 7～23 ms |

### 可重現與續訓

- 固定種子、deterministic 演算法、每個 epoch 的洗牌由（種子, epoch）決定；測試確認「訓練 1 個 epoch → 中斷 → 續訓」與一次訓練完的權重逐位元相同（CPU）。
- 每次訓練記錄設定、每個 epoch 的指標、PyTorch／CUDA 版本與 GPU；資料庫 `model_versions`、`training_runs`（Alembic 遷移 0004）登記模型與訓練紀錄。

### 限制

- **策略本身高度可被剝削**（見上方）：網路不能直接當作近似 GTO 的 Agent 使用。
- **只學到 solver 在這些題目上的策略**：題目的範圍是合成的（見 M6），下注抽象固定；評估的是「模仿 solver」的程度，不代表對真人或其他尺寸的表現。標示為 `NEURAL_APPROX`。
- **還沒有接成 Agent**：實際牌局中需要估計雙方的範圍，並以即時求解為主（設計稿：`docs/realtime-agent.md`）。

### 每個決策怎麼做、怎麼標示

| 情況 | 做法 | strategy_source |
|---|---|---|
| 翻前 | push/fold 解（短籌碼）或規則型 | `SOLVER_APPROX` 或 `HEURISTIC` |
| 翻牌 | 深度限制的即時求解：翻牌、轉牌有下注，河牌直接發完比牌，每個決策最多 10 秒 | `SOLVER_APPROX`（原因欄位寫「depth-limited」） |
| 轉牌、河牌 | 以實際狀態為根即時求解，每個決策最多 10 秒 | `SOLVER_APPROX`（原因欄位寫迭代次數、達到的可被剝削量、耗時） |
| 求解失敗（記憶體、時間） | Policy Network | `NEURAL_APPROX` |
| 沒有網路模型檔 | 規則型 | `HEURISTIC` |
| 三人以上的翻牌後 | 規則型 | `HEURISTIC` |

- **以實際狀態為根**：子賽局從這條街開始，重播這條街已經發生的下注（實際金額），所以對手用樹外尺寸時不需要動作轉換。驗證：中途建立的子樹與完整樹裡對應的子樹完全相同。
- **範圍追蹤**（公開信念，不含自己的私人資訊）：翻前依每位玩家的翻前路線取前 X% 範圍（啟發式；有對手模型時寬度依對手的實際頻率調整）；翻牌後自己的動作用自己實際採用的策略更新（精確），對手的動作則在他行動當下重新求解、把他實際下的尺寸加進樹裡，再乘上每組牌選這個動作的機率。這個機率沒有對手資料時用均衡策略（self-play 假設），有 M8 的對手模型時用依對手頻率「傾斜」後的均衡策略（見下方「結果（接上 M8 對手模型）」）。
- **時間預算**：每個決策 10 秒，包含建樹、更新對手範圍（最多 30%）與求解；PyTorch 與 CUDA 在建立 Agent 時就先初始化，不佔用第一個決策的時間。

**1. 精確的正面對決（V2 測試集 90 題）**：即時求解（10 秒內）負責一方、網路負責另一方，把兩者的策略寫進同一棵賽局樹精確計算期望值，再交換位置（鏡像），沒有發牌運氣的噪音：

|---|---|---|---|---|
| 河牌 | 60 | 0.39% | **+0.065** [+0.023, +0.107] | 68% |

| 2 秒 | 21% 底池 | 3.1% 底池 |

**3. Arena（300 手，預算 2 秒）**：即時求解 vs 網路 −5.6 bb/100 [−11.1, −0.1]；vs 規則型 +17.8 [−8.3, +43.9]。這組數字參考價值有限：2 秒時轉牌求解還沒收斂（約 21% 底池），而且雙方翻前、翻牌用相同的規則型邏輯，80 手中只有約 12 個決策走到轉牌或河牌，要用 Arena 分出差距需要上萬手。上面的精確正面對決才是主要證據。

### 結果（B 階段：翻牌）

翻牌的完整樹太大，無法在 10 秒內求解，所以用**深度限制**：只有前幾條街有下注，之後直接發完比牌，葉節點的值是對所有剩餘發牌的精確勝負（兩兩勝負矩陣，與明確展開的子樹完全等價，有測試）。Agent 用**深度 2**：翻牌、轉牌有下注（翻牌 33%／75%，轉牌 75%，加注 100%，最多 2 次加注），河牌直接發完。

### 結果（C 階段：safe re-solving）

**問題**：每次決策都用「估計的雙方範圍」當根範圍重新求解（unsafe re-solving）。範圍估錯時（翻前啟發式、假設對手照均衡打，之後的 M8 對手模型也可能錯），重新求解的策略會針對錯誤的範圍，可能比原本的策略更容易被剝削。

**做法**：re-solve gadget（Brown & Sandholm 2017，以對手先驗範圍加權）：子賽局開始前，對手的每組牌可以選「離開，拿目標值」或「進入子賽局」，對手在子賽局裡的範圍 = 先驗範圍 × 進入機率。目標值是**前一次求解**中對手在目前節點的反事實值，所以重新求解不能讓對手任何一組牌拿得比前一次求解多。`BatchedSubgameCFR(..., gadget=Gadget(player, cfv))`；Agent 預設 `resolving="safe"`，前一次求解的樹找不到目前節點時（每手牌翻牌後第一個求解、超出抽象的下注尺寸）退回 unsafe，原因欄位都會寫明。

**實驗**（`scripts/experiments/safe_resolve_turn.py`，V1 測試集轉牌題 8 題）：轉牌完整樹只求解 20／60／200 次迭代當「藍圖」（Agent 10 秒的轉牌求解停在幾 % 底池，相當於 20～60 次）；我方保留藍圖的轉牌策略，把每個河牌子賽局（每條轉牌路線 × 每張河牌）重新求解，再放回完整樹，計算**我方在完整賽局的可被剝削量**（對手對整體策略做最佳回應）。四種做法：只用藍圖、unsafe、safe（目標 = 對手的最佳回應值 CBV，理論上安全）、safe（目標 = 對手的藍圖期望值，Agent 用的做法）。

範圍正確（重新求解用藍圖推出的範圍），可被剝削量中位數（% 底池）：

| 藍圖 | 只用藍圖 | unsafe | safe（CBV） | **safe（期望值）** |
|---|---|---|---|---|
| 20 次迭代 | 6.37 | **3.66** | 5.51 | 3.89 |
| 60 次迭代 | 0.93 | **0.47** | 0.79 | 0.56 |
| 200 次迭代 | 0.11 | **0.08** | 0.12 | **0.08** |

範圍估錯（對手範圍每組牌乘上 exp(N(0,1)) 的雜訊，或「過時」：忽略對手在轉牌的動作），藍圖 60 次迭代：

| 範圍錯誤 | 只用藍圖 | unsafe | safe（CBV） | **safe（期望值）** |
|---|---|---|---|---|
| 雜訊 | 0.92 | 1.10（4/8 題比藍圖差） | 0.78 | **0.57** |
| 過時 | 0.92 | 2.14（8/8 題比藍圖差） | 0.79 | **0.63** |

（藍圖 20 次迭代時，雜訊：unsafe 3.85、safe 3.93；過時：unsafe 4.77、safe 4.00。）

- **unsafe** 在範圍正確時最好，但範圍一錯就可能比不重新求解還差（過時範圍時 8 題全部變差）。
- **safe（CBV）** 理論上安全，但目標太保守：對手幾乎都選擇離開，我方子賽局的策略得不到訓練，改善很小。
- **safe（期望值）** 在 40 種「題目 × 情境」組合中**從未比藍圖差**；範圍正確時只比 unsafe 少一點改善（0.56% 對 0.47%），範圍錯誤時明顯最好。所以 Agent 預設用它。
- 對均衡對手的期望值也是同樣的趨勢（例如藍圖 60 次、過時範圍：unsafe −0.57%、safe −0.29%、藍圖 −0.44% 底池）。

### 結果（接上 M8 對手模型）

**做法**（`backend/opponent/ranges.py`）：對手行動時，重新求解得到的均衡策略先混入 2% 均勻（容許失誤），再做最小 KL 的「傾斜」：讓範圍加權後各類動作（棄牌／過牌／跟注／下注／加注）的頻率等於目標頻率，同一類裡各尺寸的比例與「哪些牌做什麼」的順序都保留。目標頻率 = 對手在這個情境（例如轉牌被下注）的觀察次數，以均衡自己的頻率為先驗中心、20 個虛擬觀察收縮；沒有觀察時就是均衡。翻前範圍寬度改由對手在最後一個翻前動作情境的頻率決定，同樣以原本的啟發式寬度為中心收縮。Agent 在每手結束時（`hand_over`）用公開資訊更新對手模型；決策原因會寫「opponent ranges: opponent model (N hands)」或「self-play assumption」。

**評估**（`scripts/experiments/opponent_ranges.py`）：Agent 先有對手 1,000 手的歷史（對手與規則型 Agent 對戰的公開資訊），再與對手單挑並持續學習。每個翻後決策時，同一條公開歷史上同時追蹤三種範圍：模型修正（實際用來打）、self-play、self-play 加上同樣的 2% 失誤容許（消融：分出改善有多少只是來自容錯）。三者用同樣的重新求解，只差模型做的修正。分數是對手**真實手牌**在範圍中的對數機率（越高越好；均勻範圍約 −6.96），差距以同一個決策配對、以手牌為群集計算 95% 信賴區間。種子 84：

|---|---|---|---|---|---|---|
| 規則型（依手牌） | 140 | **−6.20** | −7.43 | −7.36 | −6.96 | **+1.16** [+0.72, +1.60] |
| 純網路 Agent（依手牌、接近均衡） | 55 | **−6.01** | −7.28 | −7.07 | −6.96 | **+1.07** [+0.68, +1.45] |
| 跟注站 | 117 | −7.06 | −10.48 | −9.85 | −6.94 | **+2.80** [+2.02, +3.57] |
| style-station | 80 | −7.88 | −9.00 | −8.67 | −6.95 | **+0.79** [+0.06, +1.53] |
| style-nit | 135 | −7.94 | −8.88 | −8.57 | −6.96 | **+0.63** [+0.14, +1.12] |
| style-maniac | 23 | −7.37 | −10.06 | −9.06 | −6.96 | +1.69 [−0.44, +3.81] |

- 模型修正在有足夠樣本的 5 種對手上都顯著比 self-play（含容錯）準；2% 容錯本身只貢獻一小部分。
- 對依手牌決策的對手（規則型、純網路），模型修正後的範圍比均勻範圍更準，self-play 範圍反而比均勻範圍差：翻前啟發式寬度與「對手照均衡打」的假設偏差都不小。
- 對與手牌無關的對手，三種都比均勻範圍差（均衡的「哪些牌做什麼」本身就不對），模型只能修正頻率。

### 限制

- **翻牌是深度限制求解**：河牌的下注被忽略（河牌直接發完比牌），對完整解的偏差見上方 B 階段結果。求解失敗時翻牌沒有網路可用（網路沒有翻牌訓練資料），退回規則型。
- **翻前深籌碼範圍是啟發式**（沒有已求解的深籌碼翻前資料）。
- **對手模型只修正頻率，不修正「哪些牌做什麼」**：對與手牌無關的對手（跟注站、隨機），範圍仍比均勻範圍差；範圍更準也不等於贏更多，期望值的效果要在 M9 驗證。Arena 每手重建 Agent，所以只有網頁對戰與實驗腳本會跨手學習。
- **safe re-solving 的目標值是估計值**：用前一次求解的對手期望值（不是最佳回應值），沒有理論上的安全保證；實驗中從未比藍圖差，但樣本是 8 題。每手牌翻牌後的第一個求解沒有前一次求解可用（翻前範圍是啟發式），仍是 unsafe。
- **對手範圍更新的時間**：上限是預算的 30%（3 秒），但建樹與 CUDA graph 擷取是固定成本，翻牌上實測最多約 3.7 秒。
- **速度**：10 秒預算下一手牌可能要幾十秒，不適合大量 Arena 模擬；網頁對戰中 AI 在執行緒裡思考，不會卡住伺服器。


## M8 驗收結果

**結論：✅ 通過（門檻版本 2，新種子重跑）。** 第一次執行（門檻版本 1）只有 G2 的「RMSE 比值」沒過，原因是門檻設計：兩個檢查點比較的估計值集合不同。依專案原則，版本 1 的結果照實保留；新門檻 G2′ 在重跑**之前**寫進 `backend/opponent/acceptance.py`，再用全新的種子（評估與參考模擬都換）判定。

### 做了什麼

- **統計**（`backend/opponent/stats.py`）：只用公開資訊（盲注、籌碼、動作序列、攤牌亮出的牌）。公開動作序列用引擎本身重播（下注規則與牌無關），所以每個決策點的合法動作與情境判斷和引擎完全一致。每個統計是一組共用分母的結果，資料庫存「機會數／發生數」（設計文件第 6 節）：
  - **決策情境**（每個決策恰好屬於一個）：翻前 `pf_open`／`pf_option`／`pf_vs_raise`／`pf_vs_3bet`／`pf_vs_4bet`，翻後每條街 `unbet`（過牌／下注）、`vs_bet`、`vs_raise`（棄牌／跟注／加注）。只有在所有結果都合法時才計入（例如面對全下時不能加注，不算）。這些是範圍追蹤與 Exploit Engine（M9）要用的。
  - **摘要統計**：VPIP、PFR、3-bet、fold to 3-bet、翻牌 c-bet、fold to c-bet、WTSD、W$SD。
  - 位置依按鈕推算（單挑：BTN、BB；多人：BTN、SB、BB、UTG…CO）。
- **後驗**（`backend/opponent/model.py`）：每組結果用 Dirichlet 共軛後驗（二元時是 Beta），平均值、90% 等尾可信區間、機會數一起給出。兩層收縮：玩家層 = 族群先驗 + 所有位置的計數；位置層 = 以這位玩家**其他位置**的後驗平均為中心、最多 20 手權重的先驗 + 這個位置的計數。純 Python（網頁伺服器沒有 NumPy），Beta 分位數與 digamma 自己實作，和 SciPy 比對誤差 < 1e-11。
- **族群先驗**：`fit_prior` 用經驗貝氏（Dirichlet-multinomial 最大概似，Minka 定點法）從一群玩家的計數擬合。**目前沒有可合法使用的真人資料**（HandHQ 的授權還沒確認），所以預設是每個結果 1 個虛擬計數的弱先驗，來源欄位寫明。
- **儲存**：`player_statistics`、`opponent_models` 兩張表（遷移 `0005`）；網頁對戰每手牌結束時更新。
- **已知風格的 Agent**（`backend/agents/style.py`）：nit、tag、lag、station、maniac。每個決策情境依固定機率選結果、與手牌無關，所以真實頻率就是參數，可以精確驗收。它們是測試用的對手，不是策略（標為 `HEURISTIC`）。

### 版本 1 的 G2 為什麼沒過（事後分析，促成版本 2）

- **比較的集合不同**：1,000 手時有 3,650 個估計值；10,000 手時多了 150 個 1,000 手時還沒有任何機會的少見情境（例如面對 4-bet），它們的 RMSE 是 0.144。
- **RMSE 被少見情境主導**：10,000 手的平方誤差有 97% 來自 1,000 手時機會數不到 30 的估計值；這些估計值在 1,000 手時被先驗拉近，比值自然偏高。依 1,000 手時的機會數分組，30 次以上的比值是 0.29～0.36，和理論值相符。

### 限制

- **族群先驗是弱先驗**：沒有真人資料；用 AI 對戰資料擬合的先驗不代表真人（設計文件第 12 節）。
- **風格 Agent 與手牌無關**：驗收的是估計器本身，不是「讀牌」；依賴手牌的 Agent 只用參考模擬驗證。
- **只驗收單挑**：統計與位置支援 2～9 人，但驗收實驗是單挑。
- **已接進即時求解 Agent**（見「即時求解 Agent」的「結果（接上 M8 對手模型）」）；用後驗來剝削對手是 M9。

## M9 驗收結果

**狀態：證據限制版精確評估通過前置檢查；正式 Arena 未通過 E1。** 門檻在第一次執行前寫進 `backend/opponent/m9.py`，維持版本 1。不得把「沒有顯著負值」當成 M9 驗收通過。

RTX 4060 Laptop 8 GB 上用 `--deals 200 --seconds 2 --workers 1`。原定三個 workers 的 GPU contexts 合計溢用約 1.1 GiB shared memory，已在第一批完成前中止並改成單 worker；Windows GPU 計數器紀錄在 `out/m9/workers3_gpu_memory.json`。只調整執行平行度，驗收門檻、牌數、種子與每步時間預算不變。

### 做法

- **Data-biased response**（`Exploit`，`backend/solver/subgame_gpu.py`；Johanson & Bowling 2009）：子賽局求解時，對手在每個決策點以機率 p 照「對手模型」行動、其餘 1 − p 自由行動（由 CFR 訓練，就是會反擊的那部分）；我方的 CFR 對這個混合體求最佳策略。「照模型行動」= 對手當下的策略做最小 KL 的頻率傾斜，讓範圍加權後各類動作的頻率等於他在這個情境（例如河牌被下注）的觀察頻率。
- **相對傾向**（`backend/opponent/exploit.py`）：對手模型記的是「這個情境的整體頻率」，但依手牌與範圍決策的對手，在不同局面的頻率差很多，整體平均套到單一局面會誤導（見下方「第一版的教訓」）。所以剝削用的是**相對於 GTO 基準的倍率**：對手頻率（以參考頻率為中心、20 個虛擬觀察收縮）÷ GTO 基準 Agent 在同樣環境（單挑對規則型 Agent）的頻率；求解時把倍率乘在**這個節點**對手自己的頻率上再正規化。打法接近 GTO 的對手倍率接近 1，幾乎不剝削；跟注站的「跟注」倍率遠大於 1。沒有參考模型時不剝削。
- **證據限制**：相對倍率仍會把強牌造成的高跟注頻率誤認為弱點，因此不再對所有情境啟用。雙方 VPIP 都至少有 20 次觀察，且對手 VPIP 的 95% 區間下界高於參考模型上界時，才使用完整倍率。其他對手只處理 `*_vs_bet` 的過度棄牌：至少 20 次觀察、參考情境有實際觀察、棄牌後驗平均高於參考頻率、95% 區間下界大於 1/3，並在每個節點再檢查實際下注尺寸的純詐唬損益兩平棄牌率。只調整「棄牌」倍率，跟注與加注倍率維持 1。這些是方法的啟用條件，Arena 的驗收門檻維持版本 1。
- **範圍調整同步受限**：M9 啟用時，翻前只在上述寬範圍證據成立時使用 M8 的範圍調整；翻後只調整有證據的情境。只有過度棄牌證據時，範圍追蹤保留混入 2% 失誤後的基準跟注／加注比例，並且不降低該基準的棄牌頻率。`exploit=False` 時仍可單獨使用原本的 M8 範圍模型。
- **信心**：p = 0.8 × n / (n + 50)，n 是該情境的觀察數：資料少時接近 GTO，資料多時才大幅偏離（設計文件第 10 節「剝削強度隨後驗信心遞增」）。和 safe re-solving、M8 的範圍追蹤一起使用。
- **Agent**：`RealtimeAgent(exploit=True)` 為預設；通過證據條件時決策求解才剝削，原因欄位寫「exploiting the opponent model at N nodes (confidence up to p)」。`unrestricted exploitability` 是目前求解賽局未套用 Exploit 限制的策略差距，包含被刻意偏向的對手策略；不能當作受限賽局的收斂證明或我方策略的安全保證。正式效果由精確 EV 與 Arena 驗證。`opponent_model_path` 可以帶入已知對手的模型（Arena 用）。
- **範圍**：只剝削翻後（翻牌、轉牌、河牌）。翻前仍是規則型。
